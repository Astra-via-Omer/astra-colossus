Provider rates and calculation

Input and output rates are USD per million tokens. Cached input is part of input, and reasoning is part of output; neither is added twice. Cost per token and cost per processing minute use only calls with known cost. Processing time is request latency, including provider wait time, and overlapping calls are summed.

Route / provider modelInput / 1MCached input / 1MOutput / 1M

Rates are configured on the server and saved with each call. Unconfigured rates or unreported usage stay unavailable. Estimates exclude hosting, taxes and other provider charges. A stale process has no confirmed completion record.

OPERATOR DOCUMENTATION

From connection to operation.

Use the gateway across Astra systems, then build and validate engines.

Connect an Astra system

  1. Register a provider connection and add its API credential.
  2. Register a model alias and its native provider model name, output limit and prices.
  3. Set up the calling system and its monthly budget and request limit.
  4. Issue a system key with explicit model grants and store it on the calling backend.
  5. Call Colossus and follow usage, cost and processing status from this console.

Provider credentials stay server-side. Configuration APIs require an active administrator session. Approved participants can use the engine room.

Preserve user attribution
Send the user’s Astra bearer token in Authorization and the backend’s system key in X-Colossus-Service-Key. Colossus verifies both identities. A system key alone records the system without inventing an end user.
Supported serving contracts
Chat: POST /v1/chat/completions. Embeddings: POST /v1/embeddings on an embedding route. Anthropic text/image conversations are normalized through the Messages adapter; its tool calls are not enabled in this gateway. Existing /v1/runs and engine evaluation APIs remain available.

1. Sign in with your Astra account


  1. Start on the Colossus welcome page.
  2. Enter the same email and password you use for Astra Workflow or Lab, then select Sign in.
  3. The server checks your active account and role before opening this engine room. Review Your account and access above for your current permissions.


Active Astra admins and participants with Colossus approval can enter the engine room. Participants can run saved engines and download results using their assigned model group. Administrators can also monitor all users, create and test versions, and evaluate engines.


If your session expires or access is revoked, you return to the welcome page. Use Sign out when you finish. The browser uses your shared Astra account; service keys are reserved for backend API callers.







2. Run your first source


  1. In Validate a source, choose Evidence review · 1.0.0. Use Focused claim check when you want to focus on a specific question.
  2. Give the document a Source ID, such as measurement-2026, and the excerpt a Section ID, such as page-1. Keep these IDs meaningful so you can trace the result back.
  3. Paste the actual excerpt into Evidence. Start with a short paragraph; this form accepts one source section of up to 60,000 characters.
  4. In Review focus, describe the question you want checked. For example: “Check the capacity claim and identify missing measurement conditions.”
  5. Select Run validation, then look in Result below the forms.


TRY THIS EXAMPLE
Measured capacity is 20 units in 2026.
This example supplies a claim but no measurement method. Look for the model's assessment and proposed next check.
Loads the fields only when Evidence is empty. You choose when to run it.






3. Read and keep the result


  1. Open Result. The report is JSON: each item in claims is an accepted, traceable claim.
  2. Check its quote, sourceId and sectionId against your original excerpt.
  3. Read assessment for limitations and nextCheck for the evidence you should collect next.
  4. Review excluded for claims rejected by quotation or rating checks. Correct the source or instructions if needed.
  5. Select Download result to keep the report. Colossus does not store your source text, run results or evaluation reports for later retrieval.


Identity, support and reasoning
Model-assigned scores from 0 to 2. Higher values mean the model assessed that dimension as stronger.
Importance
A score from 1 to 5 for decision impact, not confidence.
Gravity distance
An evidence-gap index from 0 to 100. Lower values mean smaller assessed gaps. It weights identity at 20%, support at 60% and reasoning at 20%.
Status: unverified
A matched quotation confirms traceability to your supplied text. It does not confirm that the source's claim is true.







4. Define your own engine


Admin step


  1. In Make an engine your own, enter a readable Name, such as “Capacity evidence check”.
  2. Choose an Engine ID, such as capacity-check. Use 2–64 lowercase letters, numbers and hyphens, starting with a letter.
  3. Start with Version 1.0.0. Choose a new ID if that ID and version already exist.
  4. Select a configured Model route. Start with astra-default, the shared provider connection.
  5. Write Instructions describing what to assess, which evidence matters and what gaps to identify. Put document content in Evidence, not here.
  6. Keep the Output token limit at 4,000 to start. The allowed range is 256–8,000.


EXAMPLE INSTRUCTIONS
Assess capacity claims using only the supplied sources. Identify the measured value, date and test conditions. Distinguish measurements from assumptions. Flag missing methods and propose the next evidence check.


Colossus supplies the claims output format automatically. Your instructions guide the review; they do not define a new output format.







5. Test your draft before saving


Admin step


  1. Keep your draft fields filled in Make an engine your own.
  2. Fill the source and review focus in Validate a source. Draft testing uses those source fields and your draft instructions, regardless of the saved engine selected in the dropdown.
  3. Select Test draft. This makes a provider call but does not save an engine version.
  4. Review the result. Does it quote the source correctly, expose missing evidence and suggest a useful next check?
  5. Refine the instructions and test with another representative excerpt. Download useful results before another run replaces them.


Try both a well-supported source and one with missing evidence. A useful engine should make limitations explicit in both.







6. Save and select an engine version


Admin step


  1. Once you are satisfied with the draft, check its ID, version, model route and instructions.
  2. Select Save engine version. Saving publishes its definition to the shared registry without making an inference call.
  3. Look for Engine version saved. in Result. The new version becomes selected in Engine version.
  4. Run the saved version on a source to check the published definition.
  5. Select Export manifest if you want a local JSON copy of the definition in your draft fields.


Saved versions cannot be edited or overwritten. When you change instructions, a model route or the token limit, save a new version, such as 1.0.1. Keep the ID to group versions of the same engine. To return to an older version, select it from the dropdown.







7. Evaluate a saved version


Admin step


  1. Choose the saved version to evaluate in Engine version under Validate a source. Evaluation uses this exact version, not your unsaved draft.
  2. In Check an engine against fixtures, supply a JSON list of 1–8 test cases. The form starts with one example.
  3. For each case, provide name, input and minClaims. You can add requiredQuote for a quotation you expect the result to include.
  4. Select Run evaluation. Each case makes a provider call, so begin with one or two short cases.
  5. Review each case's passed value in Result. A case passes when it meets the accepted claim minimum, matches the expected quotation when provided and excludes no claims.
  6. Download the report and keep it with your engine's release evidence. If a case fails, review the source and draft, then publish and evaluate a new version.


Show the example case


requiredQuote must equal an accepted claim's quotation after whitespace normalization. A passing suite checks these fixture expectations; it does not certify model accuracy.









Help when something does not work

Sign-in fails or the session expires
Use your existing Astra credentials and sign in again. If your account is inactive or you cannot sign in to Workflow either, contact your Astra administrator.
Create, Test draft or Run evaluation is disabled
These actions require admin access. Publishing also requires the shared registry to be available.
“This engine version already exists”
Change the version, such as 1.0.0 to 1.0.1, or use a different engine ID.
The quotation does not match or no claims pass checks
Use the exact source excerpt and ask for quotations from it. Check the identified source and section. Model output can still fail validation; review the reported error or excluded claims.
Output is truncated
Use a shorter excerpt or increase the draft's output token limit, then test again. Save a new version if you change a published engine.
The provider is busy or needs credits
Retry later for a busy provider; contact the service administrator for provider credit or configuration issues. A new run can incur another provider charge.




Connect another application or use transcripts
A developer can call POST /v1/runs with an engine ID, its exact version and source sections. The base URL is https://colossus.astra-via.com. Keep service keys on the calling backend. Lab, Workflow and Evidence need their own gateway integration; opening Colossus does not connect them automatically.
You can paste a transcript into Evidence. The API also accepts timestampMs on a source section. Camera capture, audio transcription, live video sessions and the Observer agent are not available in this release.
